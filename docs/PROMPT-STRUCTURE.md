# 发送给模型的内容（1.0.12）

正文、小手机、HTML 共用资料构建流程。不是将所有数据按一个固定顺序平铺，也不是完整复刻酒馆正文生成管线。

1. 开头一条 system 标明当前角色和用户人物名字。已去掉旧版默认要求“采用用户要求的平行设定”的引导。
2. 使用瞬息选中的预设条目及排序，保留条目角色、normal／continue 条件和深度插入。人物描述、性格、场景、示例对话、面具描述、激活的世界书依照预设对应插槽进入消息。世界书深度条目单独插入历史。
3. 自定义预设完全没有定义某个原生资料插槽时，在历史前补齐对应资料；若已有同样的宏展开内容则不重复。预设已定义但关闭的插槽不恢复。无预设时按世界书前置、人物描述／性格／场景、面具、示例对话、世界书后置加入非空内容，并加入角色的 system_prompt（如果有）。
4. 历史放到预设 chatHistory 插槽，没有该插槽时放到预设条目之后。历史内部依次是：创建时选择的酒馆上下文（保留 user／assistant 身份）→用户的番外要求→累计剧情总结（如果有）→总结之后的已生成章节及各节要求。
5. 最后追加一条 user，说明本次模式、目标字数／条数、续写要求、输出格式和标题要求。正文要求自然段、可用的 Markdown 格式、独立标题标签；小手机包含消息类型、表情映射、通话／撤回等协议；HTML 包含文档结构、交互、移动适配和沙盒能力。HTML 不按字数或消息数补写。

## 额外请求

字数／条数不足时，会追加补足要求及已有内容后继续请求。每十节的累计总结由单独请求生成（剧情记录员提示）；正文漏标题时有单独拟题请求。连接测试是单独的短请求，不参与故事。详情以 src/prompt.js、src/generation.js、src/story-title.js 为准。

## 为什么可能与正文表现有差异

只读取用户选定数量的普通聊天消息，不含整场聊天的全部历史。人物、面具、预设、世界书及选定上下文在创建时冻结，续写沿用该篇资料快照，并在超过十节后采用累计总结。已有作品不会因为本次更新自动重抓当前酒馆资料。

预设的复杂宏、世界书递归／计时／向量等、正文的生态脚本和全部原生提示流程并非完整复现，范围见 API-COMPATIBILITY.md。另有插件输出协议、番外要求、API 模型与采样参数等差异，不能保证角色表现与酒馆正文完全一致。本版修复上下文角色被压成一条说明、自定义预设漏人物插槽的问题，不额外添加人物性格或剧情设定。
