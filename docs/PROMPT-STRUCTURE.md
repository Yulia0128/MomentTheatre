# 发送给模型的内容（1.0.12）

正文、小手机、HTML 共用资料构建流程。不是将所有数据按一个固定顺序平铺，也不是完整复刻酒馆正文生成管线。

1. 开头一条 system 标明当前角色和用户人物名字。已去掉旧版默认要求“采用用户要求的平行设定”的引导。
2. 使用瞬息选中的预设条目及排序，保留条目角色、normal／continue 条件和深度插入。人物描述、性格、场景、示例对话、面具描述、激活的世界书依照预设对应插槽进入消息。世界书深度条目单独插入历史。
3. 自定义预设完全没有定义某个原生资料插槽时，在历史前补齐对应资料；若已有同样的宏展开内容则不重复。预设已定义但关闭的插槽不恢复。无预设时按世界书前置、人物描述／性格／场景、面具、示例对话、世界书后置加入非空内容，并加入角色的 system_prompt（如果有）。
4. 历史放到预设 chatHistory 插槽，没有该插槽时放到预设条目之后。历史内部依次是：创建时选择的酒馆上下文（保留 user／assistant 身份）→用户的番外要求→按时间覆盖的旧累计总结、百节总结、十节摘要和近期正文及其要求。完整记录不被预算裁剪，裁剪仅作用本次请求副本。
5. 最后追加一条 user，说明本次模式、目标字数／条数、续写要求、输出格式和标题要求。正文要求自然段、可用的 Markdown 格式、独立标题标签；小手机包含消息类型、表情映射、通话／撤回等协议；HTML 包含文档结构、交互、移动适配和沙盒能力。HTML 不按字数或消息数补写。

## 额外请求

字数／条数不足时，按自动补足开关和额度追加补足要求及已有正文；重试计入额度，手动补足一次仅发一条补足请求。正文漏标题时仍有单独拟题请求。连接测试是单独的短请求，不参与故事。

1.2.7 起，每第 10、20、30……节在同一次正文请求中附带 `<shunxi-summary>` 分段摘要；每第 100、200……节还附带 `<shunxi-century>` 大总结。正文／小手机在前，摘要在后；摘要为独立解析的保留标签，流式接收和编辑保存都不把它计入正文／消息。旧独立总结与格式纠正请求已取消。漏摘要或摘要截断不另发请求，不阻止续写，不增加重试按钮。

摘要覆盖已有本节正文与本轮新增正文；分轮补足后只接受最后一轮同答的摘要，较早轮的摘要仍在原始回复中留存，但不能冒充最终摘要。正文与可用摘要一起保存，修改章节会使受影响摘要／大总结失效。200—300 字和 300—500 字均为提示目标，无字数硬门槛。

普通前情预算 60000 字符，近期默认两节优先；整数十节同答摘要时为最近九节及历史摘要预留 200000 字符。缺摘要用旧累计总结与正文节选兜底，不补历史 API。超预算只节选请求副本，摘要中的关键事实、未决线索与近期情境优先，存档不变。整个请求仍有原先一百万字符上限。

同答十节摘要时，本次实际最大输出在用户设置上临时增加 1200 token；百节时增加 2800 token，仍受设置框架 200000 上限约束。用户设置原值不改。不同服务商和模型有自己的上限，需以真实 API 验收；不保证所有连接接受该最大值。

## 为什么可能与正文表现有差异

只读取用户选定数量的普通聊天消息，不含整场聊天的全部历史。人物、面具、预设、世界书及选定上下文在创建时冻结，续写沿用该篇资料快照及上述分层前情。已有作品不会因为本次更新自动重抓当前酒馆资料。

预设的复杂宏、世界书递归／计时／向量等、正文的生态脚本和全部原生提示流程并非完整复现，范围见 API-COMPATIBILITY.md。另有插件输出协议、番外要求、API 模型与采样参数等差异，不能保证角色表现与酒馆正文完全一致。本版修复上下文角色被压成一条说明、自定义预设漏人物插槽的问题，不额外添加人物性格或剧情设定。


## 1.1.7 小手机会话协议

模型根据用户要求和会话情境选择格式，无 UI 切换选项。用户明确指定优先；既有群聊只有两人发言仍是群聊；未指定时我方与一位对方为私聊，同一会话三人及以上为群聊。提及、引用和角色卡人物总数不作为群聊人数。

私聊在小手机块内首行写 `[私聊]`，消息仍是 `[char|23:48|到家了吗？]`；群聊首行 `[群聊|群名]`，消息使用 `[成员:林舟|17:20|在校门口等你们。]`，我方始终 `user`。群名和成员姓名固定，补写重复会话标记；兼容补写漏标记时沿用当前会话。所有消息类型沿用原字段，群聊转账备注写明对象。解析只作用显示副本，编辑仍保留完整 AI 回复。

本地表情只把名称与描述交给模型，图片在章节表情快照中冻结，避免把图片编码带入生成／续写上下文。
